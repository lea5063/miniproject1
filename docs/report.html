프리인보이스 (FreeInvoice)

프리랜서를 위한 견적서·인보이스 발행 관리 서비스
2반 · 이름
2026. 09.

1. 서비스 개요

1-1. 서비스명 및 배경

견적은 카톡이나 메일로 보내고, 승인됐는지는 나중에 클라이언트한테 다시 물어봐야 알고, 입금 확인은 따로 엑셀에 적어둔다. 주변 프리랜서 몇 명에게 물어보니 다들 이런 식으로 일하고 있었다. "이 견적 승인됐던가?", "이 사람 입금 아직 안 됐나?" 같은 걸 매번 기억에 의존해서 확인하는 셈이다.

프리인보이스는 이 흐름 하나를 통째로 웹 서비스 안에 넣어본 것이다. 프리랜서가 거래처별로 견적서를 써서 보내면, 클라이언트가 직접 로그인해서 승인이나 거절 버튼을 누르고, 승인된 건은 인보이스로 넘어가 입금 여부까지 확인한다. 기능을 욕심내기보다 이 한 줄기 흐름이 끊기지 않고 굴러가게 만드는 데 집중했다.

클라이언트가 프리랜서 쪽에서 미리 등록해둔 이메일로 회원가입하면, 서버가 그 이메일을 보고 기존 거래처 레코드에 자동으로 계정을 붙인다. 그래서 프리랜서는 클라이언트가 실제로 가입했는지 여부와 상관없이 거래처 정보를 먼저 등록해둘 수 있다.

3. UI 흐름

와이어프레임 대신 실제로 돌려본 화면을 그대로 캡처해서 순서대로 붙였다.

① 로그인 화면 — 이메일/비밀번호로 로그인. 신규 사용자는 회원가입으로 이동.
② 회원가입 화면 — 프리랜서/클라이언트 역할을 선택 후 가입. 클라이언트로 가입 시 이메일이 일치하는 기존 거래처와 자동 연결됨.
③ 프리랜서 대시보드 — 발송한 견적서 수, 승인 대기, 승인 완료, 미수금 현황을 요약하고 최근 견적서 목록을 노출.
④ 거래처 관리 — 신규 거래처 등록 폼과 등록된 거래처 목록(가입 여부 포함) 관리.
⑤ 견적서 작성 — 거래처 선택 후 품목명/수량/단가를 라인아이템으로 입력하면 항목별 금액과 합계가 자동 계산됨. 임시저장 또는 즉시 발송 선택 가능.
⑥ 견적서 상세 (승인완료 상태) — 승인된 견적서에서 프리랜서가 지급 기한을 입력해 인보이스를 발행하는 화면.
⑦ 클라이언트 견적 승인/거절 — 클라이언트 계정으로 로그인하여 발송된(SENT) 견적서를 확인하고 승인 또는 거절 버튼으로 의사결정.
⑧ 인보이스 목록 — 발행된 인보이스 번호, 금액, 지급기한, 결제 상태(미결제/결제완료/기한초과)를 목록으로 확인.
⑨ 인보이스 상세 — 프리랜서가 실제 입금을 확인한 뒤 "입금 확인 처리" 버튼으로 결제 상태를 수동 변경.
⑩ 클라이언트 대시보드 — 클라이언트 관점에서 받은 견적서 수와 미결제 금액을 동일한 형태로 요약.

4. 데이터 모델 설계 (ERD 요약)

전체 내용은 2반_이름_프리인보이스-DB.dbml 파일에 있다. 여기서는 테이블 5개만 짚는다.

테이블주요 컬럼설명
usersid, email, password, name, role, company_name프리랜서/클라이언트 통합 사용자 테이블. role로 구분
clientsid, freelancer_id(FK), client_user_id(FK, nullable), company_name, email프리랜서가 관리하는 거래처. client_user_id는 실제 가입 전까지 NULL
quotesid, freelancer_id(FK), client_id(FK), status, total_amount견적서 헤더. status(DRAFT/SENT/APPROVED/REJECTED)로 흐름 관리
quote_itemsid, quote_id(FK), name, quantity, unit_price, amount견적 라인아이템. amount는 서버가 자동 계산
invoicesid, quote_id(FK, unique), invoice_number, total_amount, due_date, status승인된 견적서 1건당 인보이스 1건. status(UNPAID/PAID/OVERDUE)
설계 포인트
clients를 users와 굳이 나눈 건, 프리랜서가 아직 가입도 안 한 거래처를 미리 등록해둘 수 있어야 했기 때문이다. 나중에 그 이메일로 실제 가입하면 연결되는 식. 가격 쪽은 quote_items.amount, quotes.total_amount 둘 다 서버에서만 계산해서 저장한다. 프론트에서 계산한 값을 그대로 믿었다가는 요청을 조작해서 금액을 바꿔치기할 수 있다. invoices.quote_id에는 unique를 걸었다. 견적서 하나에 인보이스가 두 번 발행되는 걸 애플리케이션 로직이 아니라 DB가 직접 막게 하고 싶었다.

6. 고려사항

6-1. 설계하면서 막혔던 부분

가장 오래 붙잡고 있었던 건 클라이언트 쪽이었다. 프리랜서가 견적을 보내려는 상대가 아직 이 서비스에 가입도 안 한 사람일 수 있다는 게 문제였다. 처음에는 그냥 클라이언트도 프리랜서처럼 먼저 가입부터 하는 걸 전제로 짜려고 했는데, 실제로는 "거래처 등록 → 견적 발송 → 그제서야 상대가 가입" 순서가 훨씬 자연스러웠다. 그래서 clients 테이블에 client_user_id를 nullable로 두고, 나중에 같은 이메일로 가입하면 자동으로 연결되게 바꿨다.

금액 계산도 한 번 걸렸던 부분이다. 처음엔 프론트에서 수량×단가를 계산해서 그대로 서버에 넘기는 식으로 짜려고 했다. 그런데 이렇게 하면 요청 값만 바꿔서 견적 금액을 낮춰 보낼 수 있겠다는 생각이 들어서, 결국 서버가 품목 리스트만 받고 금액은 직접 다시 계산해서 저장하도록 고쳤다.

상태값도 처음에는 자유롭게 왔다 갔다 하게 뒀었다. 그런데 클라이언트가 이미 확인한 견적서를 프리랜서가 몰래 다시 수정할 수 있다는 게 마음에 걸려서, DRAFT→SENT→APPROVED/REJECTED, UNPAID→PAID처럼 한쪽 방향으로만 넘어가게 막아버렸다.

6-2. 다음에 이어서 한다면

시간 관계상 이번엔 손대지 못한 부분들이다. 입금 확인을 지금은 프리랜서가 수동으로 누르는데, PG(결제대행사) 연동이 붙으면 이 버튼 자체가 없어질 것이다. 견적서를 PDF로 뽑아서 메일로 바로 보내는 기능, 클라이언트가 거절할 때 사유를 남기고 금액을 조정해서 다시 보내는 재협상 흐름, 그리고 해외 클라이언트를 받는다면 다중 화폐·부가세 처리도 다음 단계에서는 필요할 것 같다.
