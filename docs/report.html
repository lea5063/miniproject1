프리인보이스 (FreeInvoice)

프리랜서를 위한 견적서·인보이스 발행 관리 서비스
2반 · 이름
2026. 09.

1. 서비스 개요

1-1. 서비스명 및 배경

프리랜서는 클라이언트마다 견적을 메신저, 메일, 한글/워드 파일로 각기 다른 형식으로 보내고, 승인 여부와 입금 현황을 별도로 기억하거나 엑셀로 관리하는 경우가 많다. 이 과정에서 "이 견적 승인됐던가?", "누구한테 아직 입금을 못 받았지?" 같은 혼선이 반복적으로 발생한다.

프리인보이스는 프리랜서가 거래처(클라이언트)별로 견적서를 작성·발송하고, 클라이언트가 직접 로그인해 견적을 승인/거절하며, 승인된 건에 대해 인보이스(청구서)를 발행하고 입금 여부를 확인할 수 있도록 하나의 흐름으로 묶은 B2B2C 웹 서비스이다.

클라이언트는 프리랜서가 거래처로 먼저 등록해둔 이메일로 회원가입하면, 서버가 자동으로 기존 거래처 레코드와 계정을 연결한다. 이를 통해 프리랜서는 클라이언트의 가입 여부와 무관하게 거래처 정보를 미리 관리할 수 있다.

3. UI 흐름

실제 구현된 화면을 기준으로 주요 흐름을 순서대로 정리하였다.

① 로그인 화면 — 이메일/비밀번호로 로그인. 신규 사용자는 회원가입으로 이동.
② 회원가입 화면 — 프리랜서/클라이언트 역할을 선택 후 가입. 클라이언트로 가입 시 이메일이 일치하는 기존 거래처와 자동 연결됨.
③ 프리랜서 대시보드 — 발송한 견적서 수, 승인 대기, 승인 완료, 미수금 현황을 요약하고 최근 견적서 목록을 노출.
④ 거래처 관리 — 신규 거래처 등록 폼과 등록된 거래처 목록(가입 여부 포함) 관리.
⑤ 견적서 작성 — 거래처 선택 후 품목명/수량/단가를 라인아이템으로 입력하면 항목별 금액과 합계가 자동 계산됨. 임시저장 또는 즉시 발송 선택 가능.
⑥ 견적서 상세 (승인완료 상태) — 승인된 견적서에서 프리랜서가 지급 기한을 입력해 인보이스를 발행하는 화면.
⑦ 클라이언트 견적 승인/거절 — 클라이언트 계정으로 로그인하여 발송된(SENT) 견적서를 확인하고 승인 또는 거절 버튼으로 의사결정.
⑧ 인보이스 목록 — 발행된 인보이스 번호, 금액, 지급기한, 결제 상태(미결제/결제완료/기한초과)를 목록으로 확인.
⑨ 인보이스 상세 — 프리랜서가 실제 입금을 확인한 뒤 "입금 확인 처리" 버튼으로 결제 상태를 수동 변경.
⑩ 클라이언트 대시보드 — 클라이언트 관점에서 받은 견적서 수와 미결제 금액을 동일한 형태로 요약.

4. 데이터 모델 설계 (ERD 요약)

전체 ERD는 2반_이름_프리인보이스-DB.dbml 파일을 참고. 핵심 테이블 구조는 다음과 같다.

테이블주요 컬럼설명
usersid, email, password, name, role, company_name프리랜서/클라이언트 통합 사용자 테이블. role로 구분
clientsid, freelancer_id(FK), client_user_id(FK, nullable), company_name, email프리랜서가 관리하는 거래처. client_user_id는 실제 가입 전까지 NULL
quotesid, freelancer_id(FK), client_id(FK), status, total_amount견적서 헤더. status(DRAFT/SENT/APPROVED/REJECTED)로 흐름 관리
quote_itemsid, quote_id(FK), name, quantity, unit_price, amount견적 라인아이템. amount는 서버가 자동 계산
invoicesid, quote_id(FK, unique), invoice_number, total_amount, due_date, status승인된 견적서 1건당 인보이스 1건. status(UNPAID/PAID/OVERDUE)
설계 포인트
· clients를 users와 분리한 이유: 프리랜서가 아직 가입하지 않은 거래처도 미리 등록·관리할 수 있어야 하기 때문. 이메일 기준으로 사후 연결.
· quote_items.amount, quotes.total_amount는 클라이언트가 임의로 조작할 수 없도록 항상 서버에서 재계산 후 저장.
· invoices.quote_id에 unique 제약을 두어 견적서당 인보이스 중복 발행을 DB 레벨에서 방지.

6. 고려사항

6-1. 설계 상의 고민

  • 클라이언트-거래처 매칭 시점: 프리랜서가 거래처를 먼저 등록하는 시나리오와 클라이언트가 먼저 가입하는 시나리오가 모두 가능해야 했다. 이메일을 매칭 키로 사용해 어느 쪽이 먼저든 자동 연결되도록 설계했다.
  • 금액 위·변조 방지: 견적 항목 금액과 합계를 프론트엔드에서 계산해 전달받는 대신, 서버에서 항상 재계산하여 저장하도록 하여 클라이언트 측 조작 가능성을 차단했다.
  • 상태 전이 제약: 견적서 상태(DRAFT→SENT→APPROVED/REJECTED)와 인보이스 상태(UNPAID→PAID)를 단방향으로 제한하여, 이미 발송된 견적서를 임의로 수정하거나 이미 결제된 인보이스를 되돌리는 등의 데이터 정합성 문제를 방지했다.

6-2. 다음 단계 개발 시 고려 사항

  • PG(결제대행사) 연동을 통한 인보이스 자동 결제 확인
  • 견적서 PDF 다운로드 및 이메일 자동 발송 기능
  • 견적서 반려 사유 입력 및 재협상(버전 관리) 기능
  • 프리랜서별 다중 화폐/부가세 처리 대응
