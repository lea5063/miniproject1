프리인보이스 (FreeInvoice)

프리랜서를 위한 견적서·인보이스 발행 관리 서비스
2반 · 이름
2026. 09.

1. 서비스 개요

1-1. 서비스명 및 배경

견적은 카톡이나 메일로 보내고, 승인됐는지는 나중에 클라이언트한테 다시 물어봐야 알고, 입금 확인은 따로 엑셀에 적어둔다. 주변 프리랜서 몇 명에게 물어보니 다들 이런 식으로 일하고 있었다. "이 견적 승인됐던가?", "이 사람 입금 아직 안 됐나?" 같은 걸 매번 기억에 의존해서 확인하는 셈이다.

프리인보이스는 이 흐름 하나를 통째로 웹 서비스 안에 넣어본 것이다. 프리랜서가 거래처별로 견적서를 써서 보내면, 클라이언트가 직접 로그인해서 승인이나 거절 버튼을 누르고, 승인된 건은 인보이스로 넘어가 입금 여부까지 확인한다. 기능을 욕심내기보다 이 한 줄기 흐름이 끊기지 않고 굴러가게 만드는 데 집중했다.

1-2. 핵심 가치 및 주요 기능

2. 시스템 액터 정의

액터는 둘뿐이다. 견적을 보내는 프리랜서와, 그걸 받아서 승인하는 클라이언트.

Actor역할상세 제공 기능
프리랜서
(FREELANCER)		 서비스 운영 주체.
거래처 관리 및 견적/인보이스 발행
  • 거래처(회사명/담당자/이메일) 등록·수정·삭제
  • 견적서 작성(품목별 수량×단가), 임시저장, 발송
  • 발송 전(DRAFT) 견적서 수정/삭제
  • 승인된 견적서를 기반으로 인보이스 발행
  • 인보이스 입금 확인 처리(결제완료 수동 변경)
  • 본인 명의 견적서/인보이스 전체 조회
클라이언트
(CLIENT)		 견적을 받는 대상.
승인/거절 의사결정
  • 본인에게 발송된 견적서 목록/상세 조회
  • 견적서 승인 또는 거절
  • 본인에게 발행된 인보이스 목록/상세 조회
표에는 안 나와 있는데, 클라이언트 쪽 로그인은 좀 특이하게 동작한다. 프리랜서가 거래처를 등록할 때 적어둔 이메일로 나중에 그 사람이 실제로 회원가입하면, 서버가 이메일이 같은 걸 보고 알아서 계정을 거래처 레코드에 붙여준다. 그러니까 프리랜서 입장에서는 클라이언트가 아직 가입 전이든 후든 상관없이 거래처 정보부터 등록해두면 된다.

3. UI 흐름

와이어프레임 대신 실제로 돌려본 화면을 그대로 캡처해서 순서대로 붙였다.

① 로그인 화면 — 이메일과 비밀번호로 들어온다. 계정이 없으면 아래 링크로 회원가입 화면으로 넘어간다.
② 회원가입 화면 — 위에서 프리랜서인지 클라이언트인지부터 고른다. 클라이언트로 가입할 때 입력한 이메일이 프리랜서가 미리 등록해둔 거래처 이메일과 같으면, 그 자리에서 바로 연결된다.
③ 프리랜서 대시보드 — 로그인하면 바로 이 화면이다. 발송한 견적서 수, 승인 대기 건수, 미수금까지 숫자 네 개로 한눈에 보이게 했고, 밑에는 최근 견적서 목록을 붙였다.
④ 거래처 관리 — 위쪽 폼으로 새 거래처를 등록하고, 아래 목록에서 기존 거래처의 가입 여부까지 확인한다.
⑤ 견적서 작성 — 거래처를 고르고 품목·수량·단가를 한 줄씩 추가하면 금액과 합계가 바로 계산된다. 화면 하단에서 임시저장할지, 곧바로 발송할지 선택한다.
⑥ 견적서 상세 (승인완료 상태) — 클라이언트가 승인한 견적서는 이렇게 보인다. 지급 기한만 입력하면 그 자리에서 인보이스가 발행된다.
⑦ 클라이언트 견적 승인/거절 — 이번엔 클라이언트 계정으로 들어와서 본 화면이다. 발송된 견적서 내용을 확인하고 승인 또는 거절 버튼을 누른다.
⑧ 인보이스 목록 — 인보이스 번호와 금액, 지급 기한, 그리고 미결제·결제완료·기한초과 중 지금 상태가 뭔지 한 줄에 다 담았다.
⑨ 인보이스 상세 — 실제로 입금이 들어온 걸 확인했다면, 여기서 "입금 확인 처리" 버튼 하나로 상태를 결제완료로 바꾼다.
⑩ 클라이언트 대시보드 — 프리랜서 대시보드와 카드 구성은 똑같은데, 숫자가 클라이언트 입장으로 바뀐다. 받은 견적서 수와 아직 안 낸 금액이 여기 뜬다.

4. 데이터 모델 설계 (ERD 요약)

테이블은 5개로 끝냈다. 전체 컬럼과 관계는 2반_이름_프리인보이스-DB.dbml에 다 있고, 여기서는 각 테이블이 왜 필요한지만 짚는다.

테이블주요 컬럼설명
usersid, email, password, name, role, company_name프리랜서와 클라이언트를 한 테이블에 담고 role로만 구분했다.
clientsid, freelancer_id(FK), client_user_id(FK, nullable), company_name, email프리랜서가 관리하는 거래처 목록. client_user_id는 가입 전까지 비어 있다.
quotesid, freelancer_id(FK), client_id(FK), status, total_amount견적서의 헤더 부분. status 값 하나로 DRAFT부터 REJECTED까지 흐름을 다 표현한다.
quote_itemsid, quote_id(FK), name, quantity, unit_price, amount견적서에 딸린 품목 줄. amount는 입력값이 아니라 서버 계산값.
invoicesid, quote_id(FK, unique), invoice_number, total_amount, due_date, status인보이스. 견적서 하나당 딱 하나만 나올 수 있다.
설계 포인트
clients를 users와 굳이 나눈 건, 프리랜서가 아직 가입도 안 한 거래처를 미리 등록해둘 수 있어야 했기 때문이다. 나중에 그 이메일로 실제 가입하면 연결되는 식. 가격 쪽은 quote_items.amount, quotes.total_amount 둘 다 서버에서만 계산해서 저장한다. 프론트에서 계산한 값을 그대로 믿었다가는 요청을 조작해서 금액을 바꿔치기할 수 있다. invoices.quote_id에는 unique를 걸었다. 견적서 하나에 인보이스가 두 번 발행되는 걸 애플리케이션 로직이 아니라 DB가 직접 막게 하고 싶었다.

6. 고려사항

6-1. 설계하면서 막혔던 부분

가장 오래 붙잡고 있었던 건 클라이언트 쪽이었다. 프리랜서가 견적을 보내려는 상대가 아직 이 서비스에 가입도 안 한 사람일 수 있다는 게 문제였다. 처음에는 그냥 클라이언트도 프리랜서처럼 먼저 가입부터 하는 걸 전제로 짜려고 했는데, 실제로는 "거래처 등록 → 견적 발송 → 그제서야 상대가 가입" 순서가 훨씬 자연스러웠다. 그래서 clients 테이블에 client_user_id를 nullable로 두고, 나중에 같은 이메일로 가입하면 자동으로 연결되게 바꿨다.

금액 계산도 한 번 걸렸던 부분이다. 처음엔 프론트에서 수량×단가를 계산해서 그대로 서버에 넘기는 식으로 짜려고 했다. 그런데 이렇게 하면 요청 값만 바꿔서 견적 금액을 낮춰 보낼 수 있겠다는 생각이 들어서, 결국 서버가 품목 리스트만 받고 금액은 직접 다시 계산해서 저장하도록 고쳤다.

상태값도 처음에는 자유롭게 왔다 갔다 하게 뒀었다. 그런데 클라이언트가 이미 확인한 견적서를 프리랜서가 몰래 다시 수정할 수 있다는 게 마음에 걸려서, DRAFT→SENT→APPROVED/REJECTED, UNPAID→PAID처럼 한쪽 방향으로만 넘어가게 막아버렸다.

6-2. 다음에 이어서 한다면

시간 관계상 이번엔 손대지 못한 부분들이다. 입금 확인을 지금은 프리랜서가 수동으로 누르는데, PG(결제대행사) 연동이 붙으면 이 버튼 자체가 없어질 것이다. 견적서를 PDF로 뽑아서 메일로 바로 보내는 기능, 클라이언트가 거절할 때 사유를 남기고 금액을 조정해서 다시 보내는 재협상 흐름, 그리고 해외 클라이언트를 받는다면 다중 화폐·부가세 처리도 다음 단계에서는 필요할 것 같다.
